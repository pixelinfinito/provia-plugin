Supplier

1. Supplier 20 fields

Selecting the counterparty in a purchase request, comparing quotations, contracting, preparing payment and periodic supplier evaluation.

Owner: Not established by any supplied source. Proposed: Procurement maintains identification, contacts, classification and status; Finance confirms the taxpayer number and the ERP link. Confirm before setup.

Functional coverage

  • Identity and classification: Included. Trading name is the native record Name; registered name, taxpayer number and the accounting code cover the cases where the Name is not enough. Category and sub-category support finding a supplier.
  • Contacts and location: Included. One commercial contact with email and phone, plus address and country of establishment where the order depends on them.
  • Ownership and structure: Included. A relationship owner is recorded. No parent/subsidiary structure is modelled; nothing in the question suggests group-level purchasing.
  • Status and lifecycle: Included. One status field covers the whole relationship, with a registration expiry date. Qualification status was deliberately merged into it rather than kept as a second, overlapping status.
  • Operational and commercial terms: Included. Usual currency, agreed payment term and agreement validity are the terms a requester or an approver needs to see before committing. Prices are not held here; they belong to the quotation on the case.
  • Relationships: Pending. No second entity type is proposed, so there is nothing to link to yet. A link to a Contract or an Item catalogue depends on whether those objects exist and who would maintain them. See the deferred candidates in setup.
  • Evidence and source: External system. Registration documents, quotations, purchase orders and invoices stay with the case that produced them or in the document store. Only the ERP link and the registration expiry date are kept on the supplier.
  • Bank and payment details: External system. Account details are the highest-risk data in a purchasing process and have a confirmation procedure of their own in the finance system. Keeping a second copy in Provia creates a fraud surface with no owner. The ERP link covers the lookup need. Revisit only if Provia is meant to prepare payment instructions, which no supplied source says.

Setup and dependencies

  • No customer evidence was supplied. Every field, option list and owner below is a proposal to confirm against the real purchasing procedure, not a recorded requirement.
  • Native Name, UUID, creator and system timestamps already exist. No field here duplicates them, and no source_system, source_record_id, verified_at or version field was added.
  • Configure Supply category before Supply sub-category, then copy each option's parentValue exactly. Do not set a default value on the dependent field. Replace the illustrative sub-categories with the organization's real ones before creating the type; changing them later means reviewing existing records and any filters built on them.
  • Supplier code is a text field because the accounting system is assumed to assign it. If the organization has no external supplier register, replace it with an auto_number field (required false, no default, prefix SUP-, padding 4, startAt 1) and do not keep both. Automatic numbers can have gaps, are not exported in workflow YAML and cannot be edited once assigned.
  • Access: this type carries supplier contacts and the taxpayer number. The proposal is create and edit for Procurement and Finance, view for the rest of the organization so requesters can select a supplier. No access grants are declared in this catalogue because no group design exists yet; set them when the groups are defined. Field-level permissions do not exist — the sensitivity notes are guidance, not enforcement.
  • Deferred entity candidates, with reasons. Purchase request: rejected — it is one execution of a process, so it is a workflow case, not an entity; creating both would duplicate every value and leave two records to keep in step. Quotation: deferred — quotations belong to the request that solicited them; make it an entity only if the same quotation is genuinely reused across requests. Contract or framework agreement: deferred — plausible if contracts have their own renewal and review lifecycle, which no supplied source confirms; today the agreement_valid_until date covers the purchasing need. Item or material catalogue: deferred — worth having only if the organization already maintains a governed item list; otherwise a free-text description on the request is honest. Cost centre or budget line: deferred — belongs to the finance chart of accounts; model it as a select on the case, or as an entity only if finance will maintain it in Provia.
  • No entity-to-entity relationship is configured, so there is no creation-order dependency. Create Supplier first, then reference it from the purchase request workflow's entity field.
  • Manual entry walkthrough. Registering 'Demonstration Logistics' from a supplier's own registration pack, a procurement officer knows at creation: trading name (the Name), registered name, taxpayer number, category and sub-category, contact name, email and phone, address, country of establishment and usual currency. Status starts at 'Under registration'. Not known at creation: the accounting code (Finance creates the supplier there afterwards), the ERP link (same), the payment term (agreed later or never, for ad hoc suppliers), agreement validity (only if an agreement is signed), registration expiry (only once someone defines which documents are required) and both evaluation fields (empty until the first evaluation). That is why every field is required false at creation; readiness is checked before award, not at registration.
  • Unresolved maintenance effort. Three fields have no confirmed owner or update trigger: registration expiry depends on a document re-check process that may not exist; both evaluation fields depend on a supplier evaluation process that may not exist; the accounting code and ERP link depend on Finance doing a second step after registration. If those processes do not exist, remove the fields rather than ship a register that goes stale — a field nobody updates is worse than no field.
  • The taxpayer number is not verified for uniqueness. Provia does not enforce a uniqueness constraint on a custom field, so two records for the same supplier remain possible; deduplication is a manual search before creating a record.

Checks before process execution

  • Before a purchase request is awarded to this supplier, confirm the status is 'Approved for purchasing', the registration expiry is not past, and the accounting code and ERP link are filled so the order can be placed. None of this is enforced by the fields; make it a check in the award or approval action of the workflow.
  • Before payment is prepared, confirm the bank details in the finance system, not in Provia. Provia holds no account details by design.
