Functional coverage

  • Identity and classification: Included. Native Name carries the trading name; legal name, NIF, accounting code and category cover the order header, invoice matching and reporting by category.
  • Contacts and location: Included. The commercial contact receives requests for quotation and orders; address and country are needed on the order and to recognise foreign suppliers.
  • Ownership and structure: Included. One relationship owner in Purchasing maintains the record and answers questions about the supplier.
  • Status and lifecycle: Included. Relationship status distinguishes prospective, active, suspended and closed suppliers before an order is placed; approval date records when qualification happened, if the organization qualifies suppliers.
  • Operational and commercial terms: Included. Currency, payment terms, lead time and framework agreement feed the order and the budget confirmation without re-entry on each request.
  • Relationships: Case. Purchase requests and orders reference the supplier from the case (entity field on the workflow). No inverse list is kept on the supplier; Provia shows linked cases from the record.
  • Evidence and source: External system. Bank details, tax certificates and the signed contract stay in the accounting system and document repository; the record holds the accounting code and the agreement link only.
  • Performance and evaluation: Pending. A rating or last-evaluation date needs a defined evaluation process; none was supplied. Added when the evaluation cycle is confirmed (decision D5).

Setup and dependencies

  • Sources: none supplied. All fields, options and maintainers are assumptions to confirm with Purchasing and Finance.
  • Native record Name, UUID, creator and timestamps are used as-is; no display-name, source-system or provenance fields are added.
  • If the destination already has a supplier type, reuse it and reconcile these fields against its schema instead of creating a second type. The tenant could not be read in this session.
  • Creation-time required is true only for Status. Everything else can be completed after registration; the readiness list below says what must exist before an order.
  • Configure Category and Status as select fields with the option values exactly as listed; values are stable keys, labels can be translated.
  • Currency has no default: the country context is provisional. Set aoa as default only after confirming most suppliers invoice in Kz.
  • Payment-term options are illustrative company terms, not statutory. Replace with the organization's actual agreed terms.
  • Supplier code is a text field for the code assigned by the accounting/ERP system. Do not add an auto_number alongside it unless the organization has no external code at all (decision D3).
  • Manual-entry walkthrough: create «Demonstration Supplies, Lda.» knowing only trading name, category = goods, contact name/email and Status = prospective. Later: Purchasing adds NIF and address from the supplier's registration document, Finance supplies the accounting code once the supplier is created there, and payment terms/currency are filled after the first negotiation. Status moves to active when the organization decides the supplier may receive orders. NIF is entered in Provia and in accounting; the accounting system is authoritative and Purchasing copies it once (no synchronization).
  • Sensitivity: for a sole trader the NIF and phone are personal data. Restrict record access to Purchasing and Finance if the organization treats them as confidential; a sensitivity label is not permission enforcement.

Checks before process execution

  • Before an order is placed: Status = active, NIF, commercial email, currency and payment terms filled. The Status field does not block selection by itself; the order action's brief must instruct the assignee to check it.
  • Before invoice matching: accounting supplier code filled by Finance.
