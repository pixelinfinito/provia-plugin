Angola · 2 entity types

Manual setup specification. This JSON is not a Provia import contract. Icons come from the bundled reference; confirm the destination version. Copying does not create types, fields or records.

Create the types before configuring relationships. Copy each value into its corresponding field. Related type names are catalogue references, not destination IDs. Core model fields can be optional at creation.

  • No country was stated; Angola is used as a provisional context per the plugin's default (confirm with the customer). Currency and identifier formats below are illustrative only.
  • Scope: contact details needed to reach a supplier when placing and coordinating orders. This is a focused catalogue for that use, not a complete organizational supplier/procurement model — extend it if broader supplier management (contracts, evaluation, payment terms) is later in scope.
  • Declined by design: passport numbers and family details of supplier employees were requested but are not included. The requester stated there is no use for these fields. Provia entity design requires an actual business use, source and maintainer for every field, and explicitly rejects collecting sensitive data merely to appear comprehensive. Passport numbers are identity-document data and family details are relatives' personal data; neither supports contacting a supplier about an order, and collecting them without a defined process, access restriction and retention rule is a data-minimization risk with no offsetting benefit. If a specific, named use appears later (for example, ID verification for controlled site access), model that as its own field on the process that actually needs it, with restricted access — not as a default attribute of every contact record.

Setup and dependencies

  • Name is native. These fields do not duplicate UUID, creator or system timestamps.
  • Manual walkthrough: create 'Demonstration Supplier'; set category and procurement owner; leave relationship_status at prospective until vetted, then active before the first order. Legal name and tax number can be completed once invoicing starts.
  • Configure supplier_code as auto_number, required false, no default. The sequence can have gaps and is not exported in YAML; review backfill before adding this field to an existing type.

Checks before process execution

  • Before placing an order, confirm relationship_status is active and at least one Supplier Contact exists. The status field does not itself block order creation in Provia; that would need an explicit check in the ordering process.

Functional coverage

  • Identity and classification: Included. Native Name holds the person's full name; job_title and department classify their role for routing.
  • Contacts and location: Included. Email, phone, mobile and preferred channel cover how to reach this person about an order.
  • Ownership and structure: Case. No internal owner field on the contact itself; the linked Supplier's account_owner already covers internal accountability, avoiding a duplicate field.
  • Status and lifecycle: Included. status distinguishes a current order contact from someone who has left or changed role.
  • Operational or commercial attributes: Not applicable. This type models a person, not commercial terms; those belong on Supplier if ever needed.
  • Relationships: Included. supplier links the contact to its Supplier record; is_primary_contact distinguishes the default contact when several exist.
  • Evidence and source: Not applicable. No document or verification requirement was stated for reaching a contact about an order. Identity documents (passport numbers) and family details were explicitly requested but declined; see catalogue notes.

Setup and dependencies

  • Synthetic coverage example, not a mandatory template or confirmed policy.
  • Confirm owners, vocabularies, sources and access before use. No synchronization is configured.
  • Name is native and holds the contact's full name; these fields do not duplicate UUID, creator or system timestamps.
  • Manual walkthrough: create Supplier 'Demonstration Supplier' first, then create a Supplier Contact named 'Ana Santos' linked to it; set job_title, order_email and phone; leave mobile_phone and preferred_contact_channel blank if not yet known; set is_primary_contact true only for the one contact buyers should default to.
  • Create the Supplier type before Supplier Contact, since the entity field targetType 'supplier' must already exist.
  • Passport numbers and family details were requested for this type but are not included: no stated use was given, they are disproportionate to an order-contact use case, and Provia entity design requires an actual use, source and maintainer per field. Revisit only if a specific, access-restricted use is confirmed (see catalogue notes).

Checks before process execution

  • Before relying on a contact for an order, confirm status is active and order_email or phone is filled in. No field here blocks order creation automatically; that would need an explicit check in the ordering process.
