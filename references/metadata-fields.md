# Entity and workflow metadata fields

Source: Provia revision `2641364d9c1aa0aa2b76aa788ef521bcb6218118`. The bundled backend field schema and workflow YAML engine use this revision. Read this reference when defining entity fields, workflow case fields, defaults or dependencies. Destination availability still needs verification.

## Supported types

| Types | Use and stored shape |
| --- | --- |
| `text`, `rich_text` | Short text or formatted narrative, stored as strings |
| `number`, `currency`, `percentage`, `rating` | Numeric values; put currency, bounds and formatting in `config` |
| `date`, `datetime` | Date or date/time strings; use datetime when time matters |
| `boolean` | A JSON/YAML boolean, never a quoted label |
| `select`, `multi_select` | One option value or an array of option values |
| `email`, `phone`, `url`, `color` | Strings with the relevant field constraints |
| `user`, `entity`, `file` | Destination references; resolve identifiers before configuration |
| `auto_number` | Read-only identifier generated by Provia when a record is saved |

There are 19 types. Dependent selections are configuration on `select` or `multi_select`, not a `dependent_select` type. Native entity Name and UUID, and native case references, remain separate from custom metadata. Add a generated business reference only when it has a consumer; retain `text` for identifiers assigned by another system.

## Automatic numbering

Use `type: auto_number`, `required: false`, with no default. Its `config` supports:

| Key | Rule |
| --- | --- |
| `prefix`, `suffix` | Optional strings, empty by default. Nonempty values start with an ASCII letter or digit, followed by letters, digits or `. _ / # -`; maximum 20 characters each |
| `padding` | Integer from 1 to 10, default 4. Minimum digits, without truncating a longer sequence |
| `startAt` | Safe integer from 1 through 9007199254740990, default 1 |

For example, `prefix: AST-`, `padding: 4`, `startAt: 1` produces illustrative `AST-0001`. Examples are demonstrations, not values to submit or promises of the next allocated number. Client-supplied values are ignored and existing numbers cannot be edited. Do not request an AI action, form answer or mapping to fill the field.

The counter is scoped to the entity type and field, or the workflow family and field. Publication of a new workflow version continues that family's counter. Failed creates can leave gaps. YAML carries configuration, not live counters or assigned values; importing creates a new draft lineage. Do not promise globally unique or gapless numbering, annual resets or date-template interpolation.

Adding a field to existing records can backfill numbers in creation order. Removing it deletes its counter; adding it again starts over. Changing its formatting affects new numbers. Review existing values and references before proposing these schema changes; the plugin does not perform migrations.

## Dependent selections

The child declares `config.parentField`, naming a `select` field in the same entity type or workflow schema. Every child option declares `parentValue`, matching the parent's option **value**, not its display label. The child can be `select` or `multi_select`; the parent must be a single `select`. Chains are supported, but self-reference and cycles are invalid.

Define the parent first for manual setup. Every child option needs a valid parent binding. Do not assign a default to the child. For example, service category `support` can expose only service types linked with `parentValue: support`. No country-specific administrative list should be invented as legal or official data.

Stored values remain a string or string array. A selected child must belong to the selected parent; an empty parent cannot support a child selection. Parent changes clear descendants in the metadata editor. When planning API/integration updates, send coherent parent/child values rather than assuming the API performs that UI cleanup. Changing options or dependencies requires reviewing existing records, mappings and filters.

## File shapes and forms

- Workflow YAML uses `fields[].name` and `fields[].config.options`. Put `parentField`, numbering settings and other supported constraints in `config`.
- The editorial entity catalogue uses `fields[].key`, top-level `options` and optional `config`. Each option may carry `parentValue`; `config.parentField` refers to another field's `key` in that type. The HTML exposes each configuration value for copying. This catalogue is not an import payload.
- Form definitions have their own schema. In the inspected revision, the form field enum excludes `auto_number`, and form option definitions do not preserve dependent-option bindings. Do not promise these metadata features in a form or treat workflow YAML as packaging forms. Specify manual form setup and verify supported mappings separately.

Validate workflow YAML with `scripts/validate-workflow.mjs`. In addition to the pinned product checks, it rejects forbidden defaults inside `config.defaultValue` for generated and dependent fields. Validate and render entity catalogues with `scripts/build-entity-catalogue.mjs`. The catalogue checker uses the bundled field enum, config shape and automatic-number/dependent-selection rules. It also checks that synthetic child examples agree with parent examples. It does not certify every type-specific constraint or destination behavior.
