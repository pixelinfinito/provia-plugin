# Connected mode (`provia-implementer` MCP)

Provia's API Gateway exposes an MCP server, `provia-implementer`, specified in Provia feature 026 and extended by feature 027 (workflow permissions), pinned to the same product revision as this plugin's contract engine. When an implementer signs in through it, the skills can read the destination organization and create **draft** configuration on the implementer's behalf. This reference is the plugin side of that contract. Until the server is released in the implementer's environment, every skill behaves exactly as in disconnected mode; do not describe connected features as available when `org_get_context` is not offered by the host.

## Detect and pin

1. The host lists a tool named `org_get_context`. Call it once per session; record `tenantId`, `productRevision`, language and timezone in `organization` of the manifest and set `organization.mode: "connected"`.
2. Compare `productRevision` with `contractRevision` in `contracts/workflow-v1/contract-lock.json`. If they differ, say so and treat the destination as authoritative for icons (`provia://reference/entity-icons.json`) and validation (`workflow_import_draft` with `dryRun: true`).
3. Read before designing: `entity_types_list`, `groups_list`, `workflows_list`, `forms_list`, `setup_references_list`. Reuse existing types and groups instead of proposing duplicates; record what exists as `sources[]` of kind `catalogue`. `setup_references_list.permissionLevels` (`resourceTypes.workflow.levels[]`, en + pt) is the level list `--check` trusts when connected: record its `data` object in `organization.permissionLevels`; `workflow_get` with `includeAccess: true` returns the grants a workflow already holds (`{ unavailable: 'FORBIDDEN' }` when the token cannot read them).
4. Emails that `users_search` confirms become `groups[].members[].verified: true` with `source: "users_search"`; the tool is the only way to verify an email the sources do not carry. When an email is on a manual-trigger allowlist, also record a receipt `{ tool: "users_search", outcome: "no_op", resource: { kind: "user", id, email }, ref: { kind: "user", key: "<lower-case email>" } }` so `resolve-workflow-refs` can write the user id.

Nothing is published, deleted, completed, paid or notified through these tools. Publication, deletion and execution stay in the Provia UI.

## Apply, in dependency order

Offer `apply` only after the user has reviewed `project.html` and asked for it. Run each step as a dry run first, show the plan, then commit on confirmation:

1. **Entity types**: `entity_types_apply_catalogue` with `entityTypes[]` unchanged. Use `idempotencyKey: "<project.key>/entity-types/<type key>"`.
2. **Groups**: `groups_apply_plan`, parents first, members by email from `groups[].members`. Unknown emails come back as `unresolved_members`; record them as decisions, do not guess.
3. **Workflow draft**: run the bundled validator, then `scripts/resolve-workflow-refs.mjs` (assignees, sub-workflow targets, manual-trigger allowlists as group ids, `access` grants by key with the `groupRefs` map), then `workflow_import_draft` with the plan from `engine.planToImportRequest()`, `groupRefs` from the group receipts and `dryRun: true`; on a clean dry run, commit. The dry run answers `summary.access = { declared, resolved, skipped, unresolved[] }`; an `unresolved` grant (`not_found`, `ambiguous`, `not_in_organization`, `invalid_level`, `access_disabled`) is a decision, never a widened grant. Then `workflow_update_draft_actions` to set `defaultResponsibleType/Id` from the group receipts and to write the five-part descriptions.
4. **Forms**: `form_upsert` per `forms[]`, linking `actionRef` to the imported Form Fill template.
5. **Owners**: confirm every action's owner with `workflow_get`; anything still empty stays in `setup.md`.
6. **Access**: one `workflow_access_apply` call per workflow with the **whole** grant set, `mode: merge`, `groupRefs` from the group receipts, `idempotencyKey: <project.key>/access/<workflow key>/<revision>`. `scripts/plan-workflow-access.mjs` builds the request and the revision (below). Dry-run first; the dry run resolves every grantee and writes nothing. Store the aggregate receipt in `receipts[]` with `ref: { kind: "access", key: <workflow key> }` (the tool derives per-grant receipts under `<key>/<i>:<granteeType>:<granteeRef>` and revocations under `<key>/rev:<permissionId>`; do not mint one key per grantee). After the commit read `workflow_get` with `includeAccess: true` back into `workflows[].access.applied[]`: a grant counts as applied only when that read shows it, and the receipt counts only when its `unresolved[]` is empty and its key is the current operation's; the read also feeds the retained-excess review in [workflow access](workflow-access.md). When the resolved YAML carried a manual-trigger allowlist, record `triggers[].manual.applied: { at, hash }` after the import commit, with the `hash` the `apply_manual_start` item prints (allowlist contents, resolved principal ids and destination workflow id); until then the restriction is "resolved", not applied, and readiness stays blocked, and a changed list, a repointed receipt or a new destination needs a new application. Record the read-back's workflow id in `access.appliedWorkflowId` so a later re-import to another workflow does not inherit it: a read-back from another workflow marks nothing applied and instructs no revocation; read the destination again. `replace` is a separate, explicitly reviewed operation: only after a dry run whose `revoked[]` the reviewer accepted, with its own revision; `replace` with `grants: []` returns the workflow to creator-only. Failures: `INVALID_ARGUMENTS` (both or neither of `workflowId`/`workflowName`), `WORKFLOW_NOT_FOUND`, `WORKFLOW_AMBIGUOUS`, `ACCESS_UNRESOLVED` (replace only; nothing written), `IDEMPOTENCY_CONFLICT`, `INSUFFICIENT_SCOPE`. A tenant with `IMPORT_ACCESS_ENABLED` off answers `access_disabled` with zero grants: record the receipt with that warning and let `setup.md` say so instead of reporting success.

### Access operation revisions

The server fingerprints the complete request (`workflowId` or `workflowName`, `grants` as sent, `mode`, `groupRefs`), not only the grants. The plugin therefore persists each operation in `workflows[].access.operations[]` as `{ revision, idempotencyKey, hash, payload }`, where `payload` is the complete request the key was minted for and `hash` its canonical SHA-256. Before every apply, hash the request about to be sent: a match with the **latest** operation reuses its revision (a retry, sent verbatim from the stored payload); anything else — a corrected group mapping, an extra `groupRefs` entry, a switch from `workflowName` to `workflowId`, a changed grant, or a return to an earlier policy whose payload matches an older operation — mints the next revision. Reusing an older key would make the server replay that operation's result while the later policy stays in effect. A constant key or a revision that tracks part of the request answers `IDEMPOTENCY_CONFLICT`, which is the server doing its job; reusing an old key with a changed request is a plugin bug to report, not to retry.

### Verifying who can start

`capabilities.canStart` on `GET /workflows/:id` is computed for the authenticated caller only and `workflow_get` takes no member selector, so the implementer's own result says nothing about other members. Where the customer wants proof that a manual allowlist admits the intended starters, `setup.md` keeps a named verification step (an identified member of the starter group signs in and confirms the Start button); record the result in `workflows[].access.startVerification` as `{ member, at, result: canStart | cannot_start, hash }` with the fingerprint the item printed. The step clears only when the member's latest recorded result (by the instant of `at`, an ISO 8601 date-time) for the current fingerprint is `canStart` (a later `cannot_start` supersedes an earlier success); until then it is pending verification, never verified.

Store every receipt in `receipts[]` with `ref` set to the manifest key it resolves. Regenerate `project.html` and `setup.md` after each step. `idempotencyKey` values are deterministic from the project key so a repeated apply is a no-op, not a duplicate; access keys additionally carry the operation revision described above. Request `implement:permissions` in the consent for `provia-bootstrap` when the manifest declares grants, and say that it takes effect immediately.

## What stays manual

Publishing the workflow and forms, secrets values, HTTP allowlists, AI profile configuration, memory documents, page templates, tags on records, manual-trigger allowlists whose groups have no receipt, revocation of retained grants (a UI action or a reviewed `replace`), and any deletion. Say this in the handover; connected mode shortens `setup.md`, it does not empty it.
