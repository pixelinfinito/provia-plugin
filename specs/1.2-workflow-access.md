# provia-skills 1.2 — Workflow access, and the field findings of 20 September

**Status:** Ready for implementation (reviewed against the shipped feature 027 on 2026-09-21) · **Owner:** Marcos Lisboa · **Date:** 2026-09-20, revised 2026-09-21
**Baseline:** plugin 1.1.1, contract `2641364d` · **Target engine:** contract rebuilt from `processonrails` `fed8efaf0` (feature 027 committed on `master`; the rebuilt `engine.mjs` and `contract-lock.json` sit uncommitted in this checkout). Anything that reaches the tenant depends on feature 027 being deployed; production keeps `IMPORT_ACCESS_ENABLED` off until rollout step 3, so imported grants there answer `access_disabled` until then.

## 1. What was verified on the product side

The product code was read before designing the plugin change (`processonrails` at `86f4ce295`), and re-checked after feature 027 landed (`fed8efaf0`; details in `specs/027-workflow-permissions-import/`):

- The workflow permission vocabulary is `view` < `create_incident` < `edit` < `admin`, cumulative, one level per grant, validated per resource type at every write and published at `GET /api/v1/permissions/levels` (en + pt). `view` on a workflow means **view every incident of it**; "my own cases" needs no grant (creator, assignee, mention). `edit` includes publishing a version; `admin` adds grant/revoke, archive, delete. There is still no level that separates "see the definition" from "see all cases".
- An imported workflow without an `access` section has one principal with access: the importer. Org Owners/Admins see everything by role.
- **Manual-trigger `allowedUsers` / `allowedGroups` are now enforced** (027, Option A). A manual start through `POST /incidents`, the trigger's manual route or entity bulk creation by a user outside every enabled manual trigger's allowlist is refused with `403 TRIGGER_NOT_ALLOWED`, and `GET /workflows/:id` reports `capabilities.canStart`. The allowlist is a *start restriction*, not a permission: it narrows `create_incident`, never widens it, and an org Owner outside it is refused too. Exempt: `trigger_workflow` decisions, sub-workflow children, schedule/webhook/email/form triggers (form access mode is the control there), and API-client service accounts.
- The portable contract now has an `access` section (§2.1 shape). Unknown **top-level** keys are errors (`schema.unknown_key`); a `permissions:` key no longer validates green. Nested unknown keys stay warnings.
- New `organization` grantee ("everyone in the organization", pt «Toda a organização»): matches every active member of the resource's own organization, listed as one entry, never expanded.
- The importer resolves `group` grantees by **group name** (case-insensitive, accents preserved) or through a pre-resolved `granteeId` / `groupRefs` map; `user` grantees by email among active members; `organization` to the org id. Ambiguous names and unknown references are dropped and reported, never widened.
- Grants are per workflow id: they survive new versions and publication; duplication does not copy them (pinned by a product test).
- The MCP gained `implement:permissions`, `workflow_access_apply`, `workflow_get.access`, `setup_references_list.permissionLevels`, `groupRefs` on `workflow_import_draft`, and `access.grants` on catalogue entity types (§8).

Consequences for the field proposals: A1–A3 (starter lists via `allowedGroups`) now describe a working control, but a narrow one. The visibility question they were answering ("who may open the case") is still answered by grants at `create_incident`, because a starter also needs to see the workflow; `allowedGroups` is only worth emitting when the customer wants to restrict manual starts *below* the `create_incident` holders (for instance, everyone may view, HR alone may open). A4 stands, with the vocabulary corrected to the product's four levels. A6's "confirm in the product first" is answered — cross-area chaining is unaffected by grants or allowlists because the child incident is created by the platform on behalf of the decider.

## 2. Manifest (`provia-project/v1` → `v1.1`)

### 2.1 `workflows[].access`

An open purchasing workflow (any employee opens, the purchasing area sees the whole queue by source):

```json
"access": {
  "default": "creator_only",
  "grants": [
    { "grantee": "organization", "level": "create_incident",
      "reason": "Qualquer colaborador abre um pedido de compra",
      "sourceRefs": [{ "source": "pix-gc-pro-002", "section": "ambito" }] },
    { "grantee": "group:gestao_corporativa", "level": "view",
      "reason": "A área acompanha todos os pedidos em curso",
      "sourceRefs": [{ "source": "pix-gc-pro-002", "section": "responsabilidades" }] }
  ],
  "sensitivity": "internal"
}
```

A restricted payroll workflow (only Capital Humano opens; the deciders see their own cases without a grant):

```json
"access": {
  "grants": [
    { "grantee": "group:capital_humano", "level": "create_incident",
      "reason": "Executa o circuito e abre o caso mensal",
      "sourceRefs": [{ "source": "pix-gc-pro-004", "section": "percurso-1" }] }
  ],
  "sensitivity": "restricted",
  "note": "A Direcção Geral valida como decisora e vê apenas os casos que lhe são atribuídos; quem abre vê todos os casos do workflow (limitação registada em decisions[])"
}
```

Combining the two (an `organization` grant on a `restricted` workflow) is the canonical invalid example: rule 5 rejects it with an error, and a `view` grant to `direccao_geral` without `sourceRefs` on the restricted workflow fails rule 4.

- `grantee`: `group:<key from groups[]>`, `user:<email present in a source or resolved by users_search>`, `organization`, `creator`. Never a UUID (the engine rejects any UUID anywhere in the value). `creator` is documentation only: the engine accepts it, `--check` warns when its level is not `admin`, and the importer drops it.
- **Key versus name.** The manifest key is the plugin's identifier; the tenant knows the group by its *name* or its *id*. When the package writes `workflow.yaml` for a browser import, it must emit `group:<groups[].name>` (the importer matches names, not keys); when it applies through the MCP it may keep the key and pass `groupRefs` (`key → id` from the group receipts). Every `groups[]` entry therefore needs a `name` that is unique in the tenant, and `--check` warns when two groups share a name (the importer reports `ambiguous` and drops the grant).
- `level`: `view | create_incident | edit | admin`. One per grant. `[view, admin]` is an engine error.
- `sensitivity`: `open | internal | restricted`. `restricted` is what the review gate uses (rule 5 below).
- `reason` and `sourceRefs` are what make a grant reviewable with the customer; `--check` warns when `reason` is missing.
- `default` exists so silence is a declared choice, never an accident. A workflow with neither `access.grants` nor `access.default` fails `--check` (rule 3). The product mirrors this: a document without `access` imports creator-only with the warning `access_not_declared`.

### 2.2 `workflows[].ownerArea`, `groups[].kind`, `groups[].area`

- `groups[].kind`: `team | container | role`. `container` groups (parents with no actions) stop triggering «Group owns no action» (D4). `role` groups are the "one person per record" placeholders of B2 until `field:` assignees exist.
- `groups[].area` and `workflows[].ownerArea`: a short key (`gestao_corporativa`, `tecnologia`) so a cross-area start or sub-workflow call is a datum the checker can see (A6). Derived by `organization-rollout` from the sources; `--check` reports every cross-area edge without blocking.

## 3. `--check` rules for access

1. Every `group:` grantee resolves in `groups[]`; every `user:` grantee has `verified: true` somewhere in `groups[].members` or a `sources[]` entry. Error otherwise.
2. Every `level` is one of the four. When connected, the list comes from `setup_references_list.permissionLevels` (`resourceTypes.workflow.levels[].level`, in rank order); offline, from `references/provia-capabilities.md`.
3. Every workflow declares access: at least one grant, or `default: creator_only` explicitly. Error otherwise.
4. Ownership does not imply visibility. Members of a group assigned to an action already see the cases that contain their action without any workflow grant; a workflow-level `view` for that group exposes *every* case, which is exactly what a disciplinary or payroll workflow must not do. `--check` therefore never proposes `view` from `assigneeRef` alone. It reports (info) each assigned group that holds no grant, and it requires a `reason` with a `sourceRefs` entry on any `view`-or-above grant to an assigned group ("the team works from a shared queue", "the source says the area sees all requests"); on a `restricted` workflow a team grant without that source-backed justification is an error.
5. Sensitivity: a workflow with `sensitivity: restricted` must not grant `view` or above to `organization`, and any `create_incident` grant on it triggers the note that starters see all cases. Error for the first, warning for the second, until per-incident rules exist in the product.
6. Segregation: warn when one group holds `admin` and also executes a decision action in the same workflow.
7. Cross-area: report (info) every `ownerArea` boundary crossed by a start grant or a sub-workflow/`trigger_workflow` edge.
8. Allowlist coherence (new, because the product now enforces it): every `allowedGroups` key resolves in `groups[]` (error); duplicate group names in `groups[]` (warning, see §2.1); an allowlist on a workflow whose only starter is `organization` is reported as the deliberate narrowing it is (info, with the "Owners are not exempt" note). The "nobody can start manually" check is **membership-aware**, not an identifier comparison: a person may belong to both a granted group and a differently named allowlisted group, allowlists admit child groups of the listed group, direct `user:` grants and `allowedUsers` count, the creator's implicit `admin` does not bypass the allowlist, and only *enabled* manual triggers matter (one open trigger admits everyone with the start permission). A workflow with no manual trigger, or whose manual triggers are all disabled, has nothing to restrict: the product's allowlist check passes for everyone who holds `create_incident`, so rule 8 emits nothing for it. Access must still be explicitly declared under rule 3 (any grant, or `default: creator_only`); implicit creator and organization administrator access remains unchanged. Otherwise the checker computes, from `groups[].members`, `groups[].parentKey` (one level of sub-groups) and the grants, the set of people who hold `create_incident`-or-above and are admitted by at least one enabled manual trigger; when that set is empty and every membership involved is `verified`, it is an error; when any membership is unverified or the workflow is imported into a tenant whose groups the manifest does not fully describe, it reports "cannot determine who can start" as a warning with the missing evidence, never a definitive error. The product offers no way to ask this for someone else: `capabilities.canStart` on `GET /workflows/:id` is computed for the authenticated caller only, and `workflow_get` takes no member selector, so the implementer's own result says nothing about other members and a negative result cannot prove that nobody can start. Connected mode therefore does not claim a definitive answer. It records the checker's result and, where the customer wants proof, `setup.md` carries a named verification step: an explicitly identified member of the intended starter group signs in and confirms the Start button is offered (or `canStart: true` on the workflow); until that step is done the item stays "pending verification", never "verified".

## 4. YAML and package

- `workflow-package` emits the `access` section from the manifest exactly as feature 027 defines: `group:<groups[].name>`, `user:<email>`, `organization`; `creator` rows may be kept for documentation. Against the 027 engine (this checkout's rebuilt bundle) the section goes inside `workflow.yaml` and the validator is green; against a 1.1.1-locked bundle the section is written to `access.yaml` next to `workflow.yaml` and listed in `setup.md`. The package skill must never emit a `permissions:` key: the 027 engine rejects it as `schema.unknown_key` and the 1.1.1 engine drops it silently.
- `resolve-workflow-refs.mjs` keeps `granteeRef` and **adds** `granteeId` from the receipts (`group:<key>` → id) on the plan it hands to `workflow_import_draft`, or passes the same map as `groupRefs`; both are verified in-organization by the importer, and a wrong id is reported `not_in_organization` rather than trusted.
- Export round trip: `workflow_export_yaml` now writes the `access` section (one entry per grantee at its highest level, group names and user emails). A token that cannot read the workflow's grants gets a document without `access` plus the warning `access_omitted_no_admin`; the package skill must not treat that document as creator-only.
- `review-actions.mjs`: warn at 4 500 characters of `description` (D1). `references/action-configs.md`: document `missedBehavior` values (`catch-up-one`, not `run_once`) and the 50-character decision branch label limit (D2, D3), both read from the bundled engine so they cannot drift.
- Bundle note: the plugin's two auto-number affix tests (`rejects invalid affix in workflow metadata`, `rejects invalid prefix in an entity catalogue`) fail identically against the pre-027 engine at `86f4ce295`; they are pre-existing drift to fix in this repo, not a 027 regression.

## 6. Reconciliation of the 138 workflows already designed

A one-off pass (`scripts/reconcile-access.mjs`) proposes `access.grants` for every workflow in a 1.1.1 manifest from what it already holds, under the same rule 4 as fresh designs: the group or `creator` on the first action → `create_incident` (or `organization` when the first action is `creator` and the source says any employee may open); `setupNotes` matching «restrito|confidencial|disciplinar|denúncia|salarial» → `sensitivity: restricted`. `assigneeRef` groups get **no** `view` proposal: their members already see the cases that carry their actions. The pass lists each assigned group under `accessReview[]` with the question "does this team need every case?" and proposes `view` only when a `sourceRefs` entry in the manifest already says so (a queue, an area that sees all requests); otherwise the reviewer adds the grant with its justification or leaves it out. Everything proposed is written with `reason: "proposto por reconciliação"` and left for human review in `project.html`; the restricted ones are listed first. In connected mode the pass first reads the current state with `workflow_get` (`access.grants`, `granteeRef` = group name / email / org id) so the diff shown to the reviewer is real, then, after review, applies each workflow with `workflow_access_apply` in `merge` mode (never revokes; a stale reference cannot remove access). Where the field tenant's group names differ from the manifest keys, `groupRefs` from the group receipts carries the mapping.

Merge is the default because it is safe, but it is not sufficient: it keeps every grant the tenant already holds, so a workflow that already grants `organization/view` stays visible to everyone after an HR-only proposal is merged, and an existing `admin` is never lowered by a proposed `view`. The review rules of §3 judge the proposed manifest; readiness must also judge the **resulting** tenant state. After every apply (and in the reconciliation dry run, from `workflow_get.access`) the pass computes `retainedExcess[]` per workflow: grants present in the tenant that the approved manifest does not contain, or that exceed the approved level. Each retained grant is then evaluated as if the manifest proposed it, against rule 4 and rule 5 alike. It reports them in `project.html` and `setup.md`; publication readiness is **blocked** when a retained grant violates rule 5 (`organization` at `view`-or-above on a `restricted` workflow), grants `admin` outside the approved set, or fails rule 4 (`view`-or-above held by an assigned group on a `restricted` workflow with no source-backed justification in the manifest). The reviewer resolves a blocked retained grant in one of two ways, and neither is a paper exercise. Adding it to the manifest with its `reason` and `sourceRefs` makes it a proposed grant, which reruns every rule: a justification can satisfy rule 4, but nothing satisfies rule 5, so an organization-wide grant on a `restricted` workflow can only be removed. Removal (a UI revocation or the reviewed `replace` below) clears the block only when it has **succeeded** and a fresh `workflow_get.access` read no longer shows the grant; a scheduled, planned or dry-run removal leaves readiness blocked, because the access still exists. Removing excess is a separate, explicitly reviewed operation: either single revocations in the product UI, or a `workflow_access_apply` in `replace` mode with the complete approved set, run only after a dry run whose `revoked[]` preview the reviewer has accepted, with its own revision in the idempotency key.

## 7. Acceptance cases

- Purchasing SOP where any employee opens and Gestão Corporativa executes → grants `organization/create_incident` and `gestao_corporativa/view`; no `allowedGroups` in the output unless the source restricts manual starts.
- HR onboarding where everyone may view but only Capital Humano may open manually → `organization/view`, `capital_humano/create_incident`, and, only if the source says so, `allowedGroups: [capital_humano]` with rule 8 reporting the narrowing.
- Disciplinary procedure → `sensitivity: restricted`, no organization grant, `create_incident` only to Capital Humano, a `decisions[]` entry about case visibility; review gate reports the limitation.
- Manifest with a `user:` grantee whose email is not in any source → `--check` error, `setup.md` lists it as unverified.
- Manifest without `access` on one workflow → `--check` error; adding `default: creator_only` clears it and the review gate still lists the workflow as creator-only.
- Two groups with the same `name` → `--check` warning naming both; the importer would report `ambiguous`.
- Container group with no actions → no «owns no action» warning.
- Package against the 1.1.1 engine → `access.yaml` beside the YAML, never a `permissions:` key; against the 027 engine → `access` section inside `workflow.yaml`, validator green, no `workflow.access.not_declared` warning, and a deliberately injected `permissions:` key is reported as `schema.unknown_key` with `valid: false`.
- Browser import of the packaged YAML → the importer's dry run reports every grant resolved (group names, not keys) and no `access_not_declared` / `access_grant_unresolved` warning.
- Connected apply with receipts for all groups → `workflow_access_apply` dry run resolves every grantee and writes nothing; one unknown key in `merge` → that grant reported `unresolved`, the others applied, receipts `created`/`updated`/`no_op`; the same input in `replace` → `ACCESS_UNRESOLVED`, nothing written; the same root key replayed → `replayed: true`; a changed grant on the same key → `IDEMPOTENCY_CONFLICT`.
- Tenant with `IMPORT_ACCESS_ENABLED` off → import warns `access_disabled`, zero grants; the package skill surfaces the warning in `setup.md` instead of reporting success.
- Disciplinary workflow whose instructor group is only an `assigneeRef` → no `view` grant is proposed; the group is listed as "sees its own cases"; adding `group:instrutores/view` without a `sourceRefs` justification is a `--check` error on the restricted workflow and a warning elsewhere.
- Action with `assigneeRef: "field:requerente"` and fallback `creator` → YAML carries `creator`, `setup.md` lists the action as owner-set-manually, the manifest keeps the `field:` intent; without a fallback → `--check` error.
- Manual allowlist `[capital_humano]` packaged for a browser import with no group receipts → YAML has no allowlist and `setup.md` has a blocking "restrict manual start" step; in connected mode with receipts → the trigger carries the group UUID; connected with a missing receipt → `--check` error, nothing dropped.
- Tenant already granting `organization/view` on a workflow the manifest now marks `restricted` → merge dry run and `workflow_get.access` show the retained organization grant as `retainedExcess`, readiness is blocked, and only a reviewed `replace` (dry run `revoked[]` accepted) or a UI revocation clears it.
- Approved grant set changed after a successful apply → the request hash differs from the stored operation payload, a new revision is minted and the new key applies cleanly; the same for a corrected `groupRefs` mapping, an added `groupRefs` entry, or a switch from `workflowName` to `workflowId` with identical grants. A retry after a network failure reuses the stored payload and key and answers `replayed: true`. Reusing an old key with any changed request is `IDEMPOTENCY_CONFLICT` and is reported as a plugin bug, not retried.
- Restricted workflow whose assigned instructor group already holds `view` in the tenant while the manifest grants it nothing → the retained grant fails rule 4 and readiness is blocked; adding the grant to the manifest with `reason` and `sourceRefs` reruns the rules and clears it; scheduling a removal does not clear it; a completed revocation clears it only after a fresh `workflow_get.access` read shows the grant gone.
- Restricted workflow whose tenant already holds `organization/view` → adding a justification to the manifest does not clear the block (rule 5 has no justification branch); only a confirmed removal does.
- Workflow with no manual trigger, or with every manual trigger disabled → rule 8 reports nothing about starters (the product's allowlist check passes in that situation); access must still be explicitly declared under rule 3, which accepts any grant, including `view` alone, or `default: creator_only`; implicit creator and organization administrator access remains unchanged.
- Two enabled manual triggers, one allowlisted to a group that shares members with the `create_incident` grantee → rule 8 finds at least one admitted starter and reports nothing; the same manifest with an unverified membership → "cannot determine who can start" warning listing the unverified member, not an error.

## 8. Product contract as shipped (2026-09-21, for the implementer)

Portable YAML (`frontend/src/lib/workflow-io`, bundled here): `access: { default?: creator_only, grants?: [{ grantee, level }] }`. Engine issues by `rulePath`: `schema.unknown_key` (error, top level only), `workflow.access.{default,grants,grantee,level,duplicate_grantee}` (errors), `workflow.access.{creator_level,unknown_key,not_declared}` (warnings); `checks[]` gains `access`; `valid` is `false` whenever `errors[]` is non-empty. Serializer warnings: `access_omitted_no_admin`, `access_grant_unexportable`.

Importer (`POST /api/v1/workflows/import`, plan schema bundled here): `access: { default: 'creator_only', grants: [{ granteeType: group|user|organization, granteeRef, granteeId?, level }] }` (≤200). Dry run answers `summary.access = { declared, resolved, skipped, unresolved: [{ index, granteeType, granteeRef, level, reason: not_found|ambiguous|not_in_organization|invalid_level|access_disabled }] }`; commit answers `access = { granted, skipped, unresolved }`. Warnings: `access_not_declared` (path `access`), `access_grant_unresolved`, `access_grant_skipped` (paths `access.grants[i]`), `access_disabled`. The plan hash covers `access`, so a different section on the same `Idempotency-Key` is `409 IDEMPOTENCY_CONFLICT`.

MCP (`implement:permissions`, direct effect, consent bucket "takes effect immediately"):

- `workflow_access_apply` `{ workflowId | workflowName, grants: [{ granteeType, granteeRef, granteeId?, level }] (0..200), mode: merge|replace, groupRefs?, idempotencyKey, dryRun? }`. Failures: `INVALID_ARGUMENTS` (both or neither workflow selector), `WORKFLOW_NOT_FOUND`, `WORKFLOW_AMBIGUOUS` (lists ids), `ACCESS_UNRESOLVED` (replace only), `IDEMPOTENCY_CONFLICT`, `INSUFFICIENT_SCOPE`. Aggregate receipt `{ outcome, resource: { kind: workflow, id, name }, applied, revoked, remaining, unresolved, receipts, replayed? }`; item outcomes `created | updated | no_op | dry_run`. `replace` with `grants: []` returns the workflow to creator-only (implicit creator and Owner/Admin access is untouched).
- `workflow_import_draft` accepts `plan.access` and `groupRefs`; non-empty `plan.access.grants` needs `implement:permissions` (refused before any call, and again by the backend).
- `workflow_get` `{ includeAccess?: true }` → `access: { grants: [{ id, granteeType, granteeRef, granteeId, level }] }` or `{ unavailable: 'FORBIDDEN' }`.
- `setup_references_list.permissionLevels` = the `data` object of `GET /permissions/levels` (`resourceTypes.<type>.levels[]` with `rank`, `label`, `description` in en and pt; `granteeTypes`; `implicit` rules) or `{ unavailable }`.
- `entity_type_upsert` / `entity_types_apply_catalogue` accept `access.grants[]` per type (needs the scope; `permissions[]` on create, `merge` apply on update).
- Server instructions: apply order entity types → groups → workflow draft → forms → owners → access.

Trigger allowlist: `403 TRIGGER_NOT_ALLOWED` (localized), `capabilities.canStart` on `GET /workflows/:id`; exemptions as in §1.
