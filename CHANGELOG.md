## 1.2.0

- Installation remains marketplace-only. Documentation-hosted ZIP downloads stay withdrawn; the archive builder is retained for internal portability checks.

Workflow access as data, from the field findings of 20 September and Provia feature 027 (workflow permissions and import). The contract engine is rebuilt from `processonrails` `fed8efaf019abc901cb2b229f3676dc4031126fa`; it carries the `access` section, rejects unknown top-level keys (`schema.unknown_key`, so a `permissions:` key never validates) and warns `workflow.access.not_declared` on a document without access.

- **Manifest `provia-project/v1.1`.** `workflows[].access` (`default`, `grants[]` with `grantee`, `level`, `reason`, `sourceRefs`; `sensitivity`; `note`; `applied[]`; `operations[]`), `workflows[].ownerArea`, `workflows[].triggers[]` with manual allowlists as group keys, `templates[]`, `unresolvedActors[]`, `unresolvedEntityTypes[]`, `actions[].dueInSource`, `actions[].assigneeRef: field:<key>` with `assigneeFallback`, `groups[].kind`, `groups[].area`, `groups[].members[].verified` + `source`, `sources[].emails[]`, receipts of kind `access`. Published as `references/project-manifest.schema.json`. `v1` manifests are accepted with a warning; the alternate shapes agents produced (section strings, `source#anchor`, folded strings, `forms[].name`) are normalised with a warning instead of failing.
- **`--check` access rules 1–8** (`references/workflow-access.md`): grantees resolve and users are verified, levels come from the engine, every workflow declares access, ownership never implies visibility (an assigned group's `view` needs a source-backed reason; error on a restricted workflow), a restricted workflow never grants the organization `view`-or-above, segregation of `admin` and decisions, cross-area edges, and membership-aware allowlist coherence that reports "cannot determine who can start" whenever the implicit creator or an administrator could be among the admitted, with a definitive error only for an allowlist that admits nobody (empty groups marked `membersComplete: true`; a proposed list is unknown membership). Retained tenant grants (`access.applied[]`) are judged like proposals and block readiness when they violate rule 5, hold `admin` outside the approved set or fail rule 4 on a restricted workflow; only a fresh read without the grant clears the block. Infos are a third channel next to errors and warnings; the summary counts declared access, readiness blocks and unresolved keys.
- **Project map rebuilt.** `project.html` is now an application in one offline file: every object embedded once, views rendered on demand from stable fragment URLs (`#workflow/compras/action/decidir`) with breadcrumbs, browser Back/Forward and remembered scroll positions; a bounded layout with independently scrolling navigation and content, a mobile rule that wins, and print rules. It opens on a project overview (workflows by area, owners, separate statuses for design, validation, customer approval and application evidence; the configured mode and the application evidence are reported separately). Each workflow gets a review page with its execution flow drawn from the YAML sequencing (order, parallel steps, decision branches, returns, cancellations, triggered workflows), tabs for dependencies, access and review; actions show the five-part brief as sections, entity types a field table with copy controls and relationships, forms a field preview with mappings, groups their members and responsibilities, sources their sections and what cites them. Pending work becomes four review queues (design questions, validation findings from `--check`, setup to apply, blockers) with filters by workflow, area and type and browser-local review notes exportable by object id (the page states they are not incorporated). Search covers names, keys, descriptions, briefs and fields with accents ignored. Internal names are translated; the dependency graph is optional, scoped and drawn on demand. Tested at scale with a synthetic project of 1,800 actions, 300 entity types and 800 decisions, including headless-Chrome checks (skipped without Chrome).
- **Map and handover.** `project.html` gains an Acesso tab (workflow × grantee × level, retained grants, readiness) and shows access, areas, kinds, fallbacks and triggers in the detail panel. `setup.md` gains the access table, unverified emails, blocking "restrict manual start" steps, the pending `canStart` verification step in connected mode, `access_disabled` receipts and retained grants; its mode line derives from `receipts.length` (manual, partial, applied).
- **Packaging.** `scripts/emit-workflow-access.mjs` writes the `access` section by group name into the YAML (or `access.yaml` beside it for an engine that predates access) and refuses `permissions:`. `scripts/resolve-workflow-refs.mjs` also writes manual-trigger allowlists as ids from receipts (groups from group receipts, users from `users_search` receipts of kind `user`), treats an unresolved principal or a manifest manual trigger the YAML lacks as a blocking item (exit 1, never dropped silently), emits `field:` fallbacks and returns `groupRefs` plus the importer-shaped `access`. Both allowlist arrays are rewritten from the manifest (a removed principal loses the permission), labelled triggers match exactly, and an enabled YAML manual trigger the manifest does not describe is a blocking bypass. An allowlist is `unresolved`, `resolved` or `applied` (`triggers[].manual.applied: { at, hash }` bound to the list contents, the resolved principal ids and the destination workflow, plus a workflow receipt; the resolver also syncs `enabled` from the manifest); only `applied` clears the readiness block, and `verify_can_start` clears only when a member's latest recorded `startVerification` (per member and fingerprint, ordered by the parsed instant of `at`) is `canStart` against the current fingerprint, because principal ids prove the references resolve, not that the restriction exists in the tenant. `scripts/review-actions.mjs` warns from 4 500 characters. `references/action-configs.md` documents `missedBehavior` (`skip`, `catch-up-one`, `catch-up-all`) and the 50-character branch label, both read from the engine and pinned by a test.
- **Connected mode.** Apply order ends with access: one `workflow_access_apply` per workflow, `mode: merge`, `groupRefs` from the group receipts, `idempotencyKey: <project.key>/access/<workflow key>/<revision>` where the revision is minted from the canonical hash of the complete request and stored with its payload in `access.operations[]`; `scripts/plan-workflow-access.mjs` builds the request, reuses a key only for a verbatim retry, and prints the dry run first. `workflow_get.access` is read back into `access.applied[]`, and only that read marks a grant applied, matching group grants by identity first (a recorded `granteeId` must equal the group's receipt id; a name never overrides conflicting ids); an access receipt counts only when its `unresolved[]` is empty and its key is the current operation's for the current destination workflow (`access.appliedWorkflowId` binds the read-back to it, and a read-back from another workflow neither marks grants applied nor instructs revocations: the analysis and `reconcile-access` ask for a fresh read of the destination). Only the latest operation is a retry candidate, so returning to an earlier policy mints a new revision instead of replaying an old key. "What stays manual" now names allowlists without receipts and the revocation of retained grants.
- **Reconciliation.** `scripts/reconcile-access.mjs` proposes access for every workflow of an older manifest under rule 4 (first-action group → `create_incident`, restricted by the source's words, no `view` for assigned teams, `accessReview[]` questions), marks everything `proposto por reconciliação`, lists restricted workflows first, records the starters-see-all decision and computes retained excess from a `workflow_get` snapshot. A snapshot entry without a `grants` array (or with malformed grants) is an error, never an empty read that would clear a recorded block. It never edits the source or applies anything.
- **Skills.** Designer proposes `access`, `ownerArea`, allowlists only when the source restricts starts, `field:` intents with fallbacks, templates and `dueInSource`; organization-rollout owns the access matrix, kinds, areas, unique names and verified members; review fails readiness on the access rules and blocking retained grants; package emits the section and plans the apply; bootstrap fixes the shared contracts before parallel design, splits the catalogue into an initial pass, `entityRequests[]` and reconciliation, adds the access step and requests `implement:permissions`; information-model may carry catalogue `access.grants[]`.
- **Examples** move to `v1.1` with hand-written access sections (onboarding is `restricted`), `access` in every YAML (validator green, no `not_declared` warning) and regenerated maps and handovers.
- The two auto-number affix tests now use an affix the product rejects (`RE Q`); the product had already relaxed the leading-hyphen rule before 027, so `-REQ` was pre-existing drift, not a regression.

## 1.1.0

Release 1.1 of the business improvement plan: the plugin becomes an implementer toolkit with one project spine, executable action briefs and a measured evaluation loop. The YAML contract engine, fingerprints and validator are unchanged.

- **Project manifest and map (B2).** `provia-project.json` (`provia-project/v1`) holds sources with section anchors, entity types in catalogue shape, groups, workflows whose actions carry `sourceRefs`, `assigneeRef` by group key, `formRef`, `entityRefs`, `evidence`, `due` and folded steps, forms, AI profiles, decisions and receipts. `scripts/build-project-map.mjs` checks every reference, renders an offline `project.html` (rail, SVG graph, detail panel with the action brief, catalogue and pending tabs; red for unresolved, green for receipts) and generates `setup.md` from unresolved items. Every skill reads and appends the manifest.
- **Action description standard and review gate (B3).** `references/action-writing.md` defines the five-part brief to the assignee (Tarefa, Como, Evidência, Concluído quando, Excepções), folding rules, no implementer notes in descriptions and `due` from the stated service level or an open decision. `scripts/review-actions.mjs` reports missing parts, leaked notes, length and `due` per action. The five examples are rewritten to the standard with proposed deadlines; the 1.0.2 fixture has a rewritten sibling with before/after gate reports; acceptance cases added.
- **Groups as data (B4).** `provia-organization-rollout` produces `groups[]` with key, name, parent, purpose, members, source references and flags (`single_person`, `alias`, `segregation`, `requester`, `external`, `unnamed`); designer and package reference owners by key; the checker warns about owner-less actions and orphan groups.
- **Designer output (B5).** `provia-workflow-designer` classifies every source step (action, decision, folded, automation, intake, out of scope, conflict) and delivers the action table, a Mermaid flow, a YAML skeleton with full briefs and the manifest entry (`references/workflow-design-output.md`).
- Quote generated skill descriptions as YAML strings so colons and trigger punctuation remain installable; regression-test parsed frontmatter.
- **Single-source skills (B7).** `catalog.json` v2 generates the 16 `SKILL.md` files, the README tables and the English and Portuguese docs pages through `scripts/build-skills.mjs`; the shared preamble moved to `references/skill-conventions.md`, so a skill front-loads one reference instead of three.
- **Evaluation harness and release gate (B9).** `scripts/run-skill-evaluations.mjs` runs the matrix (now 48 cases, three per skill) through the Claude Code CLI with the repository as the plugin, preserves outputs, grades runs with `--judge` and records statuses; `build-release.py` refuses to package stale or untriaged evaluations unless bypassed, and records the gate result in `release.json`.
- **Entry points and triggers (B10).** New skills `provia-bootstrap` (documents → manifest → catalogue → groups → workflows → forms → validated packages → map, in one authorized run) and `provia-diagnose` (triage and improvement on supplied exports). Every skill description carries pt-AO and English trigger phrases.
- **Connected-mode contract (B1, plugin side).** `references/connected-mode.md` specifies detection of the `provia-implementer` MCP server, read-before-design, apply order with dry-run and the receipt shape with a `ref` back to the manifest; `scripts/resolve-workflow-refs.mjs` substitutes ids from receipts into a copy of the YAML. Nothing connects to Provia yet; disconnected mode is unchanged.
- Attribution header `# provia-skills <version>` on generated YAML (the product-side recording of B6 and the hosted validator of B8 are outside this repository).
